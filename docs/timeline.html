🕰️ Timeline del proyecto

RAG sobre la Minecraft Wiki — 5 iteraciones de mejora dirigidas por evidencia real, no por checklist de features.

v1 — RAG Minecraft Wiki (baseline)

🎯 Objetivo: construir el pipeline RAG clásico end-to-end sobre un dataset con alma.

Lo que salió: pipeline completo en Python puro (sin LangChain), scraping de la Minecraft Wiki vía API MediaWiki con mwclient, embeddings con all-MiniLM-L6-v2 (inglés puro), ChromaDB local, FastAPI + widget web embebible, bot Mineflayer para chat in-game, Docker para deploy.

🧠 Decisiones de orquestación

  • Sin LangChain: control total, sin abstracciones opacas que rompen entre versiones. Puedo debug cada capa yo mismo.
  • CC-BY-SA de la wiki: dataset legal para portafolio público. Dije NO a scrapear libros de Harry Potter/Sapiens por copyright.
  • Modelo monolingüe inglés: mejor performance que multilingüe cuando el corpus está en inglés. Claude traduce al responder.
  • Mineflayer en vez de Fabric mod: evita aprender Java + Gradle. ~150 líneas de JS vs. un proyecto Java completo.
  • ChromaDB local: simple, persistente, sin infra extra. Suficiente para <100k chunks.

🐛 Problemas que detecté probando

  • Retrieval imperciso: pedía "Diamond Pickaxe" y salía Anvil (porque menciona diamond).
  • Preguntas en español a corpus inglés: score bajo, chunks poco relevantes.
  • El artículo "Fortune" existía pero no salía en top-5 aunque preguntara directo por él.

📚 Lo que aprendí

  • El patrón RAG completo: retrieve → contexto → LLM → respuesta con citas.
  • Embeddings, cosine similarity, top-K.
  • Web scraping vía MediaWiki API es mucho más limpio que HTML.
  • Chunk size + overlap tradeoffs (800/150 es el sweet spot para wikis).

v2 — Calidad: Query Rewriting + Re-ranking

🎯 Objetivo: fixear el retrieval impreciso con las técnicas estándar de la industria.

Lo que salió: Claude Haiku genera 3 variaciones de la query (multi-query) + cross-encoder ms-marco reordena top-20 → top-5 con precisión mucho mayor que el bi-encoder solo. Todo detrás de feature flags QUERY_REWRITE y RERANK para A/B testing. Orquestador único en pipeline.py.

🧠 Decisiones de orquestación

  • Multi-query en vez de HyDE: mejor cobertura para queries en español sobre corpus inglés (cada variación captura un ángulo distinto).
  • Haiku para rewriter, Sonnet para respuesta: Haiku es 10x más barato + 3x más rápido, suficiente para reformular. Sonnet solo para lo que necesita razonamiento.
  • Cross-encoder local: gratis (~90 MB one-time), no API, no costo por query. Corre en CPU en ~200ms.
  • Feature flags para A/B testing: puedo comparar con/sin cada mejora empíricamente en vez de asumir.

🐛 Problemas que detecté probando

  • Crafting recipes desaparecían del texto scrapeado (bug del scraper: strip_code() borraba los templates {{Crafting}}).
  • LLM alucinaba: "No tengo info... sin embargo, sé que 3 Diamonds + 2 Sticks" — colada de conocimiento pre-entrenado.
  • Chat MC mostraba **asteriscos** literales (markdown no se renderiza).

📚 Lo que aprendí

  • Bi-encoder vs cross-encoder: por qué existen los dos, cuándo usar cada uno.
  • Tradeoff latencia vs calidad: +200ms de re-ranking vs. +10-15% precisión.
  • Feature flags como técnica de ingeniería, no solo de producto.
  • Cuándo un LLM "cuela" info pre-entrenada aunque le digas que no.

v3 — UX in-game + fix de recetas + anti-alucinación

🎯 Objetivo: hacer el sistema usable de verdad in-game.

Lo que salió: preservación de templates {{Crafting}} antes de strip_code() (30 líneas de scraper) para que las recetas SÍ estén en el corpus. Dos system prompts: SYSTEM_PROMPT_FULL (widget web, markdown + citas) y SYSTEM_PROMPT_CHAT (bot in-game, texto plano corto). Rebranding del bot a MineRag. Función cleanMarkdown() en el bot que elimina asteriscos y citas [N] antes de mandar al chat.

🧠 Decisiones de orquestación

  • Convertir templates en el scraper (30 líneas) en vez de migrar a HTML scraping (que rompía todo el pipeline). Menor blast radius.
  • API param format en vez de post-procesar en el bot: le decimos a Claude "sé breve y sin markdown" desde el prompt, ahorra tokens ($) y latencia (~1s).
  • Texto plano en el bot cuando descubrí que MC kickea clientes que envían § (código de color): solo el servidor puede enviarlos.

🐛 Problemas que detecté probando in-game

  • Bot kickeado por multiplayer.disconnect.illegal_characters al usar §.
  • SYSTEM_PROMPT_CHAT quedó demasiado defensivo ("PARA AHÍ", "honestidad > utilidad") → el modelo se autocensuraba aunque tuviera contexto válido. Pico de diamante ya no respondía.
  • Corpus incompleto: Weakness Potion y otros no estaban porque solo scrapeé priority pages para probar el fix.
  • "Tolva" no matcheaba "Hopper" en retrieval consistentemente — el rewriter dependía de que Haiku acertara.

📚 Lo que aprendí

  • MC solo permite § desde servidor, no cliente. Diferencia arquitectural importante.
  • Prompt engineering fino: balance entre defensivo y útil. "Honestidad" mal calibrada = sistema inútil.
  • mwparserfromhell es potente pero tiene límites: templates específicos requieren manejo custom.
  • Cuándo re-scrape es necesario y cuándo re-ingest basta.

v4 — Observabilidad + traducción robusta + benchmark

🎯 Objetivo: datos reales medibles para vender el proyecto con evidencia (portafolio).

Lo que salió: query logger persistente JSONL (data/logs/queries.jsonl) que graba cada request al RAG con respuesta completa. Diccionario ES→EN manual (~90 términos) que garantiza traducción determinística en el rewriter. Rebalance del SYSTEM_PROMPT_CHAT (menos defensivo, más útil). Benchmark script con backfill de las queries reales del historial. Timeline visual (esta página).

🧠 Decisiones de orquestación

  • Diccionario manual en vez de traducción dinámica con Haiku: determinístico, cero costo, cero latencia. Extensible línea a línea.
  • JSONL append-only en vez de DB: portable, versionable en git, exportable a pandas con 1 línea, sin infra.
  • Backfill del historial real en vez de golden set fabricado: las queries que fallaron en pruebas son las mejores para benchmark.
  • Gráficas después, no ahora: con 5 queries son ruido, con 50+ son historia. Primero acumular datos reales de uso.

🐛 Problemas que detecté probando

  • Regresión in-game: "cómo crafteo una tolva" seguía sin funcionar aunque Hopper estaba en el corpus → glosario ES→EN lo resuelve deterministicamente.
  • Regresión in-game: "pico de diamante" en chat devolvía "no tengo info" cuando en CLI sí funcionaba → prompt chat demasiado defensivo.
  • 🆕 (con el logger activo): al hacer 19 queries reales desde el widget, detecté que Language, Cactus, Cake, Biome/Before* dominaban en 14/19 queries. Este bug era invisible antes del logger — fue v5 quien lo arregló.

📚 Lo que aprendí

  • Observabilidad es Fase B obligatoria en RAG serio, no opcional.
  • Tradeoff manual vs dinámico en glossaries: manual gana en cero-costo y determinismo.
  • Cómo medir sin sobre-ingeniar: JSONL + un script python bastan para el 90% del valor.
  • Datos reales > golden sets fabricados. Un usuario probando 2 semanas genera mejor benchmark que 100 queries inventadas.

v5 — Filtrar corpus ruidoso (con datos reales)

🎯 Objetivo: eliminar los artículos "basura" que dominaban el retrieval en las queries reales del widget.

Lo que salió: tras 19 queries reales del widget (registradas por el logger de v4), detecté que Language, Cactus, Cake, Biome/Before*, Achievement aparecían constantemente como top-1 falso. Fix con 3 defensas complementarias: blocklist (~40 títulos + regex patterns), title boost (+0.3 al score si el título aparece en la query), score floor (0.15 → respuesta honesta sin llamar al LLM).

🧠 Decisiones de orquestación

  • Filtrar en runtime, no re-scrape: los 1039 artículos siguen ahí. Cero riesgo de perder datos, cambio reversible con env var.
  • Blocklist manual, no ML: determinístico, auditable línea a línea. Un modelo para "clasificar artículos basura" sería overkill para 40 casos claros.
  • Boost aditivo: preserva la señal semántica del cross-encoder pero premia matching directo por nombre.
  • Score floor conservador (0.15): bajo para no bloquear respuestas legítimas cortas. Ahorra $$$ y latencia cuando el retrieval no encontró nada útil.
  • Datos reales > intuición: sin el logger de v4, este problema hubiera sido invisible.

🐛 Problemas que detecté probando

  • 14 de 19 queries reales del widget devolvían artículos irrelevantes en top-1 (Cactus, Language, Cake, Biome/Before 1.18).
  • Scores del cross-encoder consistentemente en 0.0-0.006 en las queries fallidas — señal de que el reranker "sabía" que los chunks eran malos, pero no había alternativa mejor.

📚 Lo que aprendí

  • RAG en producción requiere defensas explícitas. Los embeddings + re-ranking no son suficientes cuando el corpus tiene artículos con vocabulario disperso.
  • La observabilidad de v4 fue lo que hizo detectable este problema. Sin el queries.jsonl, el patrón sería invisible.
  • La solución óptima NO es más ML (más embeddings, mejor re-ranker) sino filtros de dominio. El humano orquestador aporta ese conocimiento que ningún modelo tiene.
  • Score floor + respuesta útil es mejor UX que forzar al LLM a fabricar "no tengo info" verbose. Menos $$, menos tiempo, mejor experiencia.

🎼 Sobre orquestar en la era del AI-assisted coding

Este proyecto no lo "hice" en el sentido tradicional. No escribí cada línea de código. Lo que hice fue tomar decisiones de ingeniería fundamentadas y dirigir la iteración basándome en pruebas reales.

Mi trabajo real fue:

  1. Elegir el problema correcto. RAG sobre Minecraft, no sobre políticas del IMSS. Esa decisión determinó la vibra, el uso real, y el valor del portafolio. El código gubernamental que hice primero fue solo el warm-up.
  2. Tomar decisiones técnicas fundamentadas. Sin LangChain, con re-ranking + query rewriting, in-game con Mineflayer y no con Fabric mod. Cada decisión tiene un tradeoff que entiendo — puedo explicar por qué elegí X sobre Y en una entrevista.
  3. Probar en el mundo real y detectar bugs. La mayoría de los fixes de v2 → v4 vinieron de mí jugando Minecraft y notando que "esto no responde bien", no de tests automatizados. Ese instinto de producto es lo que separa un demo de un sistema útil.
  4. Dirigir la iteración. Cada versión resolvió problemas específicos que vi. No es una lista de features aleatorias, es un ciclo de probar → detectar → decidir prioridad → arreglar → volver a probar.
El AI fue el pair programmer que escribió el código. Yo fui el ingeniero que decidió qué código escribir, qué probar, qué priorizar, y qué desechar. En 2026, esa es la habilidad que separa a un desarrollador reemplazable de un partner técnico.

Cosas que valen la pena que veas en el código, no porque las escribí yo, sino porque las decidí:
