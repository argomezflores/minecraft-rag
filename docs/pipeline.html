⛏️ Pipeline técnico — RAG Minecraft (v3)

Este documento explica capa por capa qué hace el sistema, por qué existe cada pieza, y muestra el código real que la implementa. Está pensado para ser leído en orden (siguiendo el nav lateral) o para ir directo a la capa que te interesa.

Convenciones: cada capa tiene 4 bloques: Qué hace (para qué existe), Por qué así (tradeoffs), Código real (snippet de la función), Ejemplo (input → output).

Ingesta 1/4 Scraper — Minecraft Wiki → texto plano

Qué hace

Baja artículos de la Minecraft Wiki oficial usando la API MediaWiki. Convierte el "wikitext" crudo (con templates {{Infobox}}, links [[Diamond|diamond]]) en texto plano legible.

Por qué así

Decisión: API MediaWiki, NO web scraping HTML.
La wiki corre MediaWiki, que expone https://minecraft.wiki/api.php. Le pides "dame la página Beacon" y te devuelve JSON con el wikitext. Alternativa: bajar HTML renderizado y parsearlo con BeautifulSoup — mucho más frágil (menús, sidebars, JavaScript). La API te da contenido puro.
Librería: mwclient. Maneja paginación, rate limiting automático, y errores 429. Sin ella, la API MediaWiki es incómoda: params anidados, formato JSON verboso, cursors para paginar.

Ingesta 2/4 Chunker — dividir texto en fragmentos

Qué hace

Divide cada artículo en fragmentos (chunks) de ~800 caracteres con 150 chars de overlap. Cada chunk se convertirá en un vector independiente.

Por qué así

Tamaño 800 chars: El modelo de embeddings tiene límite de ~512 tokens (~2000 chars). Un PDF/artículo entero no cabe. 800 chars ≈ un párrafo largo = una idea completa por chunk. Con 500 se cortan ideas; con 1500 los chunks tienen mucho ruido y el retrieval es menos preciso.
Overlap 150 chars (~20%): Sin overlap, ideas que caen en el borde entre chunks se pierden. Ejemplo: si un chunk termina "the Beacon requires a base of" y el siguiente empieza "3×3 Iron blocks", ninguno tiene la idea completa. Overlap la duplica en ambos.
Separadores naturales (\n\n > \n > . > ): buscamos el mejor punto de corte dentro de la ventana. Preserva la estructura del texto.

Código real

def split_text(text: str, chunk_size=800, overlap=150) -> list[str]:
    if len(text) <= chunk_size:
        return [text.strip()]

    separators = ["\n\n", "\n", ". ", " "]
    chunks, start = [], 0
    while start < len(text):
        end = start + chunk_size
        if end >= len(text):
            chunks.append(text[start:].strip())
            break
        # Buscamos el mejor separador dentro de [start, end]
        split_at = -1
        for sep in separators:
            idx = text.rfind(sep, start, end)
            if idx > start:
                split_at = idx + len(sep)
                break
        if split_at == -1:
            split_at = end
        chunks.append(text[start:split_at].strip())
        # overlap: siguiente chunk empieza 150 chars antes
        start = max(split_at - overlap, start + 1)
    return [c for c in chunks if c]

Ingesta 3/4 Embedder — texto → vector de 384 números

Qué hace

Convierte cada chunk en un vector de 384 dimensiones que representa su significado. Textos con significado similar quedan cerca en ese espacio.

Por qué así

Modelo all-MiniLM-L6-v2: inglés puro. La wiki está en inglés y modelos monolingües rinden mejor que multilingües en su idioma nativo. Es local (no API), rápido (~200 chunks/s en CPU), gratis (~90MB one-time download).
normalize_embeddings=True: normaliza los vectores a norma 1. Efecto: producto punto de dos vectores = cosine similarity. Más rápido de computar en ChromaDB.
@lru_cache en get_model(): el modelo se carga UNA sola vez por proceso. Cargarlo tarda ~3s. Sin caché, cada query lo recargaba.

Código real

from functools import lru_cache
from sentence_transformers import SentenceTransformer

@lru_cache(maxsize=1)
def get_model() -> SentenceTransformer:
    print(f"[embedder] Cargando modelo {EMBEDDING_MODEL}...")
    model = SentenceTransformer(EMBEDDING_MODEL)
    return model

def embed_texts(texts: list[str], batch_size=32) -> list[list[float]]:
    model = get_model()
    vectors = model.encode(
        texts,
        batch_size=batch_size,
        normalize_embeddings=True,  # norma 1 → dot = cosine
    )
    return vectors.tolist()

Ingesta 4/4 Ingest — chunks + vectores → ChromaDB

Qué hace

Persiste todos los chunks con su vector y metadata en ChromaDB, una base vectorial embebida que guarda en disco (data/chroma/).

Por qué así

ChromaDB vs FAISS: FAISS es más rápido en millones de vectores pero requiere manejar índices/persistencia manualmente. Chroma es más simple: cliente persistente que guarda todo con metadata y filtros. Para <100k chunks la diferencia de velocidad es imperceptible.
ID único e idempotente (Diamond_Pickaxe_c0): si re-ingestas el mismo artículo, los chunks se sobrescriben en lugar de duplicarse. Fundamental para el flujo "actualizar corpus" sin duplicados.
Metadata rica (title, url, category, chunk_index): permite citar la fuente en la respuesta y filtrar por categoría en queries avanzadas.
hnsw:space=cosine: le dice a Chroma qué medida de similitud usar. Cosine es mejor para texto que Euclidean (L2).

Código real

def ingest_article(article: WikiArticle, collection) -> int:
    chunks = split_text(article.text, CHUNK_SIZE, CHUNK_OVERLAP)
    if not chunks: return 0

    safe_title = article.title.replace(" ", "_")
    ids = [f"{safe_title}_c{i}" for i in range(len(chunks))]
    metas = [{
        "title": article.title,
        "category": article.category,
        "url": article.url,
        "chunk_index": i,
    } for i in range(len(chunks))]

    embeddings = embed_texts(chunks)  # BATCH — mucho más rápido

    collection.upsert(  # insert-or-update
        ids=ids,
        documents=chunks,
        embeddings=embeddings,
        metadatas=metas,
    )
    return len(chunks)

Query 1/5 Query Rewriter — 1 pregunta → 3 variaciones

Qué hace

Toma la pregunta del usuario (en cualquier idioma) y pide a Claude Haiku que genere 3 reformulaciones distintas. Cada una captura un ángulo semántico distinto, lo que mejora la cobertura del retrieval.

Por qué así

Multi-query vs HyDE: HyDE (Hypothetical Document Embedding) genera una "respuesta hipotética" y busca por ella. Multi-query genera N variaciones distintas y busca por todas. Para queries en español sobre corpus en inglés, multi-query gana porque cada variación puede ser más "wiki-style".
Modelo Haiku vs Sonnet: Haiku es 10x más barato y 3x más rápido. La reformulación no requiere razonamiento profundo — variaciones léxicas y traducción. Sonnet sería overkill aquí.
Fallback silencioso: si Haiku falla (network, rate limit, JSON malformado), devuelve solo la query original. El pipeline sigue funcionando (degrada gracefully, no rompe).
Opcional (env QUERY_REWRITE=false): se puede desactivar para A/B testing o para reducir latencia en casos donde no aporta.

Código real

def rewrite_query(question: str, n: int = 3) -> list[str]:
    if not ANTHROPIC_API_KEY:
        return [question]  # fallback: sin rewriter

    try:
        client = Anthropic(api_key=ANTHROPIC_API_KEY)
        response = client.messages.create(
            model=HAIKU_MODEL,
            max_tokens=300,
            system=_REWRITE_PROMPT,  # "Devuelve JSON con 3 variaciones"
            messages=[{"role": "user", "content": question}],
        )
        rewrites = _extract_json_array(response.content[0].text)
        if rewrites:
            # Dedup + original primero
            seen = {question.lower().strip()}
            result = [question]
            for r in rewrites[:n]:
                if r.lower().strip() not in seen:
                    result.append(r)
                    seen.add(r.lower().strip())
            return result
    except Exception as e:
        print(f"[query_rewriter] fallback (error: {e})")
    return [question]

Query 2/5 Retriever — buscar top-N en ChromaDB

Qué hace

Convierte cada query (original + reformulaciones) al espacio vectorial y le pide a ChromaDB los top-N chunks más cercanos por cosine similarity.

Por qué así

Bi-encoder (rápido, imperfecto): compara query y chunk como vectores INDEPENDIENTES (calculados por separado). Es rápido — puede buscar en 150k chunks en <100ms. Pero es imperfecto: no "ve" query + chunk juntos, así que puede confundir chunks que mencionan palabras clave con chunks que son sobre el tema real.
top-N=20 (no 5) si vamos a re-rankear: lanzamos red amplia. El re-ranker filtrará después. Estándar: N ≈ 4x K final.
Score normalizado: Chroma devuelve distancia coseno (0=idéntico, 2=opuesto). Convertimos a score con 1 - dist/2 — más intuitivo para el frontend (0.87 se lee mejor que "distancia 0.26").

Código real

def search(query: str, k: int = TOP_K) -> list[Hit]:
    q_vec = embed_query(query)  # mismo embedder que en ingesta

    collection = _get_collection()
    results = collection.query(
        query_embeddings=[q_vec],
        n_results=k,
        include=["documents", "metadatas", "distances"],
    )

    hits = []
    for doc, meta, dist in zip(
        results["documents"][0],
        results["metadatas"][0],
        results["distances"][0],
    ):
        hits.append(Hit(
            text=doc,
            title=meta.get("title", "?"),
            url=meta.get("url", ""),
            category=meta.get("category", ""),
            score=round(1.0 - (dist / 2.0), 3),
        ))
    return hits

Query 3/5 Re-ranker — precisión fina con cross-encoder

Qué hace

Toma los ~20-60 candidatos del retriever y los re-ordena por relevancia semántica FINA usando un cross-encoder. Devuelve los top-K (5) mejores.

Por qué así

Cross-encoder vs bi-encoder: el cross-encoder ve (query, chunk) COMO PAR y produce un score de relevancia. Mucho más preciso porque "razona" sobre ambos juntos. Es más lento (~10ms por par) por eso NO lo usamos en el retrieval inicial — solo sobre 20 candidatos.
Modelo ms-marco-MiniLM-L-6-v2: entrenado en el dataset MS MARCO (queries reales de Bing), es el baseline estándar para re-ranking en inglés. Local (~90MB), gratis.
Sigmoide sobre el logit: el cross-encoder devuelve logits (números en (-∞, +∞)). Aplicamos sigmoide para normalizar a [0, 1] y que el score sea comparable visualmente al del bi-encoder.
Usamos la query ORIGINAL para re-rankear (no las reformulaciones). Queremos relevancia respecto a la intención real del usuario, no a nuestras variaciones.

Código real

def rerank(query: str, hits: list[Hit], top_k: int = 5) -> list[Hit]:
    if not hits: return []

    reranker = get_reranker()  # @lru_cache — carga 1 sola vez

    # El cross-encoder espera pares [(query, doc), ...]
    pairs = [(query, hit.text) for hit in hits]
    scores = reranker.predict(pairs)  # devuelve logits

    # Ordena por score DESC, toma top_k, aplica sigmoide para [0,1]
    scored = sorted(zip(hits, scores), key=lambda p: p[1], reverse=True)[:top_k]
    return [
        Hit(text=h.text, title=h.title, url=h.url,
            category=h.category, score=round(sigmoid(s), 3))
        for h, s in scored
    ]

Query 4/5 Generator — Claude Sonnet + contexto → respuesta

Qué hace

Construye un prompt con los top-K chunks re-ranked como contexto, llama a Claude Sonnet 4.5, y devuelve la respuesta en español con citas.

Por qué así

System prompt anti-alucinación: "Responde SOLO con el contexto. Si no está, dilo. No inventes." Reduce enormemente las respuestas fabricadas. Sin esta línea, el LLM "rellena" con conocimiento pre-entrenado y a veces confunde versiones.
Traducción EN → ES en un solo call: el corpus está en inglés, pero le decimos a Sonnet que responda en español. Traduce mientras sintetiza. Elimina la necesidad de un traductor intermedio.
max_tokens=512 (reducido): el chat de Minecraft es corto. Preferimos respuestas concisas. Además, respuestas largas son menos utilizables in-game.
Citas [1], [2]: le pedimos al LLM que cite el número de fragmento. El frontend luego liga cada número al link real de la wiki (solo en modo full).
🆕 v4 — Anti-alucinación endurecida: Claude a veces contradecía su propia declaración: "No tengo esa info... sin embargo, necesitas 3 Diamonds y 2 Sticks". Colada de conocimiento pre-entrenado sobre Minecraft. Nuevas reglas en el system prompt: (a) NO uses tu conocimiento pre-entrenado, (b) si dices "no tengo info", PARA AHÍ, (c) honestidad > utilidad. Reduce ~70% de casos. Para 100% haría falta un guardrail post-generation (Fase C).
🆕 v4 — Dos modos de respuesta: el generator ahora acepta format="full" (widget web, con markdown y citas [N], 512 tokens) o format="chat" (bot in-game, texto plano corto sin citas, 256 tokens). Cada uno tiene su propio SYSTEM_PROMPT_*. El bot Mineflayer usa chat — así Claude genera directo lo que el chat MC puede mostrar bien (sin post-processing ni tokens desperdiciados).

Código real

SYSTEM_PROMPT = """Eres un experto en Minecraft (Java Edition 1.20+).
Responde usando ÚNICAMENTE el contexto que se te proporciona.

Reglas:
1. Responde en ESPAÑOL aunque el contexto esté en inglés.
2. Máx 4-5 líneas.
3. Menciona items por su nombre en inglés (Diamond Pickaxe, etc.).
4. Si no está en el contexto: "No tengo información sobre eso en la wiki."
5. Cita fuentes con [N]."""

def generate_answer(question: str, hits: list[Hit]) -> str:
    if not hits:
        return "No tengo información sobre eso en la wiki."

    context = "\n---\n".join(
        f"[{i}] (Wiki: {h.title})\n{h.text}"
        for i, h in enumerate(hits, start=1)
    )
    user_msg = f"Contexto:\n{context}\n\nPregunta: {question}"

    response = Anthropic(...).messages.create(
        model=CLAUDE_MODEL,
        max_tokens=512,
        system=SYSTEM_PROMPT,
        messages=[{"role": "user", "content": user_msg}],
    )
    return response.content[0].text

Query 5/5 Orquestador — arma todo junto

Qué hace

Un solo entry point (answer_question()) que encadena rewriter → retriever → merger → reranker → generator. Es el ÚNICO lugar donde se decide qué mejora aplicar. El API y los CLIs solo llaman esta función.

Por qué así

DRY: sin este módulo, el API y el CLI duplicarían la lógica de "cuándo hacer rewriting", "cuándo re-rankear". Cambiar el flujo requeriría tocar 3 sitios.
Feature flags: QUERY_REWRITE y RERANK son env vars. Puedes A/B testear con y sin, o desactivar en dev para debug rápido.
Devuelve debug: incluye cuántas rewrites se usaron, cuántos candidatos quedaron post-dedup, etc. Útil para observability futura.

Código real

def answer_question(question: str, k: int = TOP_K) -> PipelineResult:
    debug = {}

    # 1. Query rewriting (opcional)
    queries = rewrite_query(question) if QUERY_REWRITE else [question]
    debug["rewrites_used"] = len(queries)

    # 2. Retrieval — top-N por cada query, dedup
    per_query_k = RETRIEVAL_TOP_N if RERANK else k
    raw_lists = [search(q, k=per_query_k) for q in queries]
    candidates = _merge_dedupe(raw_lists)
    debug["candidates_after_dedup"] = len(candidates)

    # 3. Re-ranking (opcional) — con query ORIGINAL, no las reformulaciones
    if RERANK and candidates:
        hits = rerank(question, candidates, top_k=k)
    else:
        hits = candidates[:k]

    # 4. Generation
    answer = generate_answer(question, hits)

    return PipelineResult(
        question=question, answer=answer,
        sources=hits, rewrites=queries, debug=debug,
    )

🔌 FastAPI — línea por línea

La API es la membrana entre el pipeline Python y el mundo exterior (widget web, bot Mineflayer, curl, futuros clientes). Aquí va comentada línea por línea:

Setup de la app

FastAPI vs Flask: FastAPI genera /docs automático (Swagger), valida tipos con Pydantic, y soporta async nativo. Flask requiere plugins para todo eso.

CORS (Cross-Origin Resource Sharing)

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],       # prod: restringir al dominio del portafolio
    allow_credentials=False,

Qué hace CORS: el navegador bloquea por default que un JS servido desde rogelio.com haga fetch a api.rogelio.com. CORS le dice "sí, permito peticiones de este otro origen". Sin esto, el widget embebido en tu portafolio no puede llamar a la API.

Modelos Pydantic — validación tipada

class QueryRequest(BaseModel):
    question: str = Field(..., min_length=3, max_length=500)
    k: int | None = Field(default=None, ge=1, le=20)

class Source(BaseModel):
    title: str
    url: str
    category: str
    score: float
    excerpt: str

class QueryResponse(BaseModel):
    question: str
    answer: str
    sources: list[Source]
    rewrites: list[str] = []
    debug: dict = {}

Qué hacen los Pydantic models: validan automáticamente el JSON entrante (rechaza queries <3 chars, k>20, etc.) y serializan el JSON saliente. Si tu handler devuelve un objeto inválido, FastAPI lanza error antes de enviar al cliente. También generan el schema para /docs.

Endpoints

@app.get("/health")
def health():
    return {"status": "ok", "service": "rag-minecraft"}


@app.post("/query", response_model=QueryResponse)
def query(req: QueryRequest):
    """Toda la lógica vive en pipeline.py — este handler solo traduce a HTTP."""
    try:
        result = answer_question(req.question, k=req.k or TOP_K)
        sources = [
            Source(title=h.title, url=h.url, category=h.category,
                   score=h.score, excerpt=h.text[:200] + "...")
            for h in result["sources"]
        ]
        return QueryResponse(
            question=result["question"],
            answer=result["answer"],
            sources=sources,
            rewrites=result["rewrites"],
            debug=result["debug"],
        )
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

Separación de responsabilidades: el handler es delgado — solo transforma HTTP → llamada Python → HTTP. Toda la lógica RAG vive en pipeline.py. Esto hace testeable el pipeline sin levantar servidor.

🎮 Bot Mineflayer in-game — MineRag

Node.js + mineflayer. Se conecta a tu mundo abierto a LAN como jugador falso (username: MineRag). Detecta !rag <pregunta> en el chat, llama al FastAPI con format:"chat", limpia el texto, aplica códigos de color MC, y publica en chunks de <240 chars con 700ms de pausa (anti-spam de MC).

¿Por qué Mineflayer y no un mod Fabric? Fabric es Java + Gradle + curva pronunciada. Mineflayer es ~150 líneas de JS con Minecraft vanilla. Trade-off: prefijo custom !rag en vez de slash-command real.

🆕 v4 — Formato in-game legible

El chat de Minecraft renderiza texto plano + códigos de formato con el símbolo §. No renderiza markdown, y muchos emojis modernos se ven como cuadrados vacíos. Por eso el bot post-procesa la respuesta:

Códigos MC usados

CódigoEfectoDónde
§aVerdePrefijo → y nombre MineRag
§fBlancoTexto de la respuesta
§7Gris claroInstrucciones tipo "Espérame"
§8Gris oscuroLínea de fuente al final
§lNegritaReemplazo de **bold** markdown
§oCursivaMensaje "Minando la respuesta..."
§rResetCierra el formato anterior
§cRojoMensajes de error

Limpieza de markdown → chat MC

function cleanMarkdown(text) {
  return text
    // **bold** → §l bold §r (bold real de MC)
    .replace(/\*\*([^*]+)\*\*/g, `${MC.BOLD}$1${MC.RESET}${MC.WHITE}`)
    // *italic* → eliminado (se ve raro en chat)
    .replace(/(?<!\*)\*(?!\*)([^*]+)\*(?!\*)/g, "$1")
    // Citas [1], [2] al final o intercaladas → eliminadas
    .replace(/\s*\[\d+\](?:\s*\[\d+\])*\s*/g, " ")
    // Emojis que no renderizan bien en chat vanilla
    .replace(/[⛏️🤖📚❌✅⚠️🎮📌✨🔍💬]/g, "")
    .trim();
}
¿Por qué también cambiamos format="chat" en la API? Sin ese flag, Claude generaría 512 tokens con markdown y luego el bot los "traduciría" a MC — desperdicio de tokens ($) y latencia. Con format="chat", Claude directamente genera texto plano corto: mejor UX, más barato, más rápido.
Skin de MineRag: en LAN con auth:"offline", MC usa el skin default (Steve/Alex) porque no hay cuenta Microsoft ligada al username. Para skin custom se necesitaría migrar de LAN a un server Paper con plugin SkinsRestorer. No se hace por costo/beneficio.

📊 Observabilidad + Benchmark (v4)

Para poder decir "mejoré el sistema" con evidencia (y no impresiones), en v4 agregamos:

Query Logger persistente

Cada request a /query se loguea en data/logs/queries.jsonl. Formato JSONL (JSON Lines) — un objeto por línea, append-only, sin base de datos.

Ejemplo de entrada

{
  "ts": "2026-08-25T21:30:00Z",
  "source": "bot",               // widget | bot | cli | unknown
  "question": "cómo crafteo una tolva",
  "format": "chat",               // full | chat
  "rewrites": [
    "cómo crafteo una tolva",                    // original
    "¿Cómo se craftea un Hopper en Minecraft?",  // Haiku #1
    "Hopper crafting recipe Iron Ingots Chest",  // Haiku #2
    "cómo crafteo un Hopper"                     // glosario ES→EN
  ],
  "sources": [{"title": "Hopper", "score": 0.891, "url": "..."}, ...],
  "answer": "Un Hopper se craftea con 5 Iron Ingots y 1 Chest...",
  "latency_ms": 3420,
  "n_candidates": 61,
  "n_final_hits": 5
}
Por qué JSONL append-only y no una DB: portable (1 archivo), versionable en git, exportable a pandas con pd.read_json(path, lines=True), sin infra extra (SQLite/Postgres), integridad garantizada (nunca modificamos líneas viejas). Para volúmenes de miles/decenas de miles de queries es óptimo.

Diccionario ES→EN manual

El query rewriter con Haiku a veces traduce "tolva" a "Hopper" y a veces no. En vez de depender de eso, agregamos un diccionario manual de ~90 términos españoles → inglés en src/mc_glossary.py. Se aplica como variación garantizada además de las de Haiku.

Manual vs. Haiku dinámico: el manual es determinístico, cero costo, cero latencia. Se extiende agregando líneas. Perdemos flexibilidad para términos que no incluimos, pero para los 90 más comunes (que cubren 95% del uso) es más robusto.

Benchmark script

El script scripts/benchmark.py ejecuta un conjunto de queries "conocidas" (backfill del historial real + las acumuladas en el log) y produce métricas objetivas:

  • Source hit rate: ¿el top-1 del retrieval es el artículo esperado?
  • Answer hit ratio: ¿la respuesta menciona los términos clave esperados?
  • Latencia p50 / p95: mediana y percentil 95 en ms.
  • Errores: queries que crashearon.

🚫 Corpus filtering (v5)

Después de v4, con la observabilidad activa, Rogelio hizo 19 queries reales desde el widget y detectó un patrón claro: los mismos artículos "basura" dominaban las respuestas fallidas:

  • Language, Achievement, Advancement, Death messages — listas con vocabulario disperso
  • Biome/Before 1.18, Biome/Before Beta 1.8 — páginas históricas obsoletas
  • Cactus, Cake, Blocking, Chat — artículos cortos que matchean por densidad léxica
  • Mine Ingredient, Funky Portal, Copper Golem Statue — meta-páginas y easter eggs

Estos artículos aparecían como top-1 en 14/19 queries reales del widget. El re-ranker daba scores 0.0-0.006 (indicando que él "sabe" que no son relevantes), pero como no hay nada mejor en el corpus para esas queries específicas, salen.

Fix 1: Blocklist explícita

Filtramos ~40 títulos + patrones regex (Biome/Before*, *April Fools*) en el retriever. Cero re-ingest, cero re-scrape — filtrado en runtime, reversible con env var.

# src/corpus_filters.py
META_BLOCKLIST_TITLES = {
    "Language", "Chat", "Achievement", "Advancement",
    "Cactus", "Cake", "Blocking", "Mine Ingredient",
    "Funky Portal", "Copper Golem Statue",
    # ... ~40 total
}

META_PATTERNS = [
    re.compile(r"^Biome/Before", re.IGNORECASE),
    re.compile(r"April Fools", re.IGNORECASE),
]

def is_blocked(title: str) -> bool:
    if title in META_BLOCKLIST_TITLES: return True
    return any(p.search(title) for p in META_PATTERNS)

Fix 2: Title boost en re-ranker

Si el título del artículo aparece como substring en la query original o en cualquier reformulación, sumamos TITLE_BOOST=0.3 al score post-sigmoide. Esto asegura que "cómo hago un hopper" siempre traiga el artículo Hopper al top. Funciona en cualquier idioma via el glosario ES→EN.

Fix 3: Score floor + respuesta honesta

Si el mejor score tras re-rank es menor a MIN_ACCEPTABLE_SCORE=0.15, cortocircuiteamos: devolvemos directamente "No encontré info específica. Intenta con el nombre en inglés" sin llamar al LLM.

Ahorros: ~$0.005 por query (llamada a Sonnet evitada) + ~2-3s de latencia. Y mejor UX (respuesta clara + hint de retry) vs. respuesta genérica larga del LLM.

🔮 Qué sigue (Fase v4)

Con este v3 el sistema es sólido para portafolio personal. Para llevarlo a "producción vendible a empresas" faltaría:

  • Evaluación con Ragas — métricas objetivas (faithfulness, context recall, answer relevance). Prioritario.
  • Hybrid retrieval (BM25 + vector) — para queries con nombres propios o siglas exactas.
  • Observability con Langfuse — trazas de cada request, latencias, costos, evolución.
  • Semantic caching — cachear respuestas de queries similares.
  • Guardrails — validar output antes de servir (jailbreaks, data leaks).
