⛏️ Guía técnica — RAG Minecraft Wiki

Un tour narrativo por el proyecto. Se lee en orden, siguiendo el flujo real de los datos: de la Minecraft Wiki hasta una respuesta con citas en el chat del juego.

🆕 Nuevo en v3: query rewriting (Claude Haiku) + re-ranking (cross-encoder). Para una explicación técnica profunda con código, snippets y tradeoffs de cada capa, mira pipeline.html.

1. ¿Qué es RAG?

Retrieval-Augmented Generation. Un LLM (Claude) es bueno redactando pero no conoce tu información específica (aquí: todos los items, mobs y mecánicas de Minecraft).

Solución RAG: buscamos los fragmentos más relevantes en la wiki oficial y se los damos al LLM como contexto. Ya no inventa — sintetiza lo que le pasaste.

Dos fases:
  • Ingesta (offline): scrapear la wiki y guardar vectores.
  • Query (runtime): cada pregunta usa esos vectores para encontrar contexto y generar respuesta.

2. Recorrido del código: Ingesta

Punto de entrada: python scripts/scrape_wiki.py seguido de python scripts/ingest_all.py --reset.

2.1. Scraping → scripts/scrape_wiki.py + src/scraper.py

Bajamos ~800 artículos de 8 categorías curadas usando la API MediaWiki (minecraft.wiki/api.php). La librería mwclient maneja rate limiting; mwparserfromhell limpia {{templates}} y [[links]].

Ética obligatoria: User-Agent identificable + 1s delay + sin paralelismo + cache local. Sin esto te bloquean.

2.2. Chunking → src/chunker.py

split_text(text, chunk_size=800, overlap=150). Cortamos en separadores naturales (\n\n > \n > . > ) para respetar la estructura.

2.3. Embeddings → src/embedder.py

Usamos all-MiniLM-L6-v2: inglés puro (mejor calidad que multilingüe para EN), local, gratis, 384 dims.

2.4. Vector store → src/ingest.py

Cada chunk se guarda en ChromaDB con: id único, texto, vector, y metadata (title, url, category).

3. Recorrido del código: Query

Punto de entrada: POST /query {"question": "..."}

3.1. Retrieval → src/retriever.py

  1. La pregunta se convierte al mismo espacio vectorial que los chunks.
  2. Chroma busca los K vectores más cercanos (K=5 default).
  3. Devolvemos texto + metadata + score.

3.2. Generation → src/generator.py

Prompt con reglas estrictas: responder en español, ser conciso (chat MC es corto), citar fuentes con [N], no inventar. Claude traduce EN → ES en un solo call.

Anti-alucinación: "Si no está en el contexto, dilo." — reduce respuestas inventadas drásticamente.

3.3. API → src/api.py

FastAPI: POST /query, GET /health, POST /ingest, GET /docs. CORS abierto para widget + bot.

3.4. Widget web → widget/chat-widget.js

JS puro con tema Minecraft (verde grass, sombras pixel). Cada fuente es link a la wiki original (atribución CC BY-SA).

4. Bot in-game → minecraft_bot/bot.js

Node.js + mineflayer. El bot se conecta a tu mundo abierto a LAN como jugador falso. Cuando escribes !rag <pregunta> en el chat:

  1. Extrae la pregunta.
  2. Llama al FastAPI local.
  3. Divide la respuesta en chunks de <240 chars.
  4. Publica cada chunk con 700ms pausa (anti-spam de MC).
  5. Cita la fuente principal al final.
¿Por qué Mineflayer y no un mod Fabric? Fabric es Java + Gradle + curva pronunciada. Mineflayer es ~50 líneas JS con Minecraft vanilla. Trade-off: usas prefijo custom !rag, no slash-command real.

5. Decisiones técnicas importantes

¿Por qué ChromaDB y no FAISS?

Chroma es más simple para <100k chunks. FAISS gana con millones.

¿Por qué modelo en inglés?

La wiki está en inglés. Modelos monolingües rinden mejor que multilingües en su idioma nativo. La traducción al español la hace Claude, mejor y en un solo call.

¿Por qué scrape + cache, no runtime?

Runtime queries deben ser <2s. Un scrape live tarda 3-5s por artículo. Además, la wiki cambia poco día a día — cachear es sano y aísla de outages.

6. Cómo modificar cosas comunes

Agregar más categorías

# scripts/scrape_wiki.py
CATEGORIES = [
    ...
    ("Structures", 60),   # ejemplo
]

Cambiar el prefijo del bot

$env:COMMAND_PREFIX = "!mc "     # ahora "!mc <pregunta>"

Ajustar top-K por request

POST /query {"question": "...", "k": 8}

7. Evolución a Agentic (Fase B)

Este RAG es reactivo. Un RAG agentic clasificaría la pregunta, buscaría en múltiples fuentes (wiki + Reddit + patch notes), detectaría respuestas incompletas y reformularía.

Herramienta: LangGraph (solo LangGraph, no LangChain). Envuelve las funciones existentes como nodos.

def rag_node(state):
    hits = search(state["question"])
    if max(h.score for h in hits) < 0.6:
        return {"next": "reformulate"}
    return {"answer": generate_answer(state["question"], hits), "next": "END"}
